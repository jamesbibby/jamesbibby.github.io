API Gateway in a Cloudflare Worker

I have been working on some CloudFlare Workers for a number of different things: serving SPAs from S3, adding special headers to certain requests, geo-redirection… and a question came up about our URL structure at work. We have a microservice architecture with domain based routing. service-a.site.com, service-b.site.com, etc.

This is a pretty standard routing when using platforms like Kubernetes, Mesosphere, Swarm, etc, but it gets in the way of the performance enhancements offered by HTTP/2 persistent connections in modern browsers.

In the old HTTP/1 world each request would open a connection to the server and close it once all the data was received. In the new HTTP/2 world a connection to the same server can be reused for mutiple requests.

Image by helix84 via Wikipedia

This may not seem like a big deal, but when all of your requests are secure (you are using HTTPS for all requsts right?) this means multiple round trips from the client to the server. Depending on the distance from the user to your servers, this could add hundereds of milliseconds for each request.

API Gateway for Performance

So you could change your routing layer or write some logic into your reverse proxy layer. Or you could do the rewriting at the edge with a CloudFlare worker.

If you make all of your service requests to a fixed domain (e.g. api.site.com/service_name) the browser can use a single HTTP/2 persistent connection to the closest CloudFlare pop and your worker can rewrite the url (service0-name.site.com) and forward the request to your service. The benifit here is that browser can use a single HTTP/2 connection back to your server for multiple requests as well, or even Argo Routing for a really optimized path)

What is a Cloudflare Worker anyway?

There are lots of names for this type of feature, lambda@edge, serverless, edge functions, etc. CloudFlare describes workers as:

…a serverless execution environment that allows you to create entirely new applications or augment existing ones without configuring or maintaining infrastructure.

Basically you can intercept a request to your servers and execute JavaScript (or any WASM code) at a CloudFlare pop.

A hello world type example would be as simple as mapping a url pattern to the following worker:

hello_world.js

// listening to the fetch event is how to intercept requests in a worker
addEventListener('fetch', event => {
  event.respondWith(new Response('hello world'))
})

All requests to that url pattern would simply return a standard HTTP 200 response with “hello world” as the payload. Simple, and you don’t need anything else, no other server, the worker returns the full response.

A Simple (more useful) Single Page Application Router

Ok so lets do something more than just returning “hello world”.

Let’s say you have a single page application and you want to host it in an Amazon S3 bucket. Combining a CDN with S3 hosting is great for both cost and performance.

One of the gotchas is that you need to separate asset requests from page requests. Any asset request needs to go back to your S3 bucket and be resolved, but any other URL needs to return the SPA (to support deep links, bookmarks, etc) The client side router will take care of showing the right content, it just needs the code bundle for the SPA.

One hack I have seen is return the index.html for any 404, but this means that an incorrect image returns your index.html page, not great.

In this (simple) example we will forward any request for an asset path to the S3 bucket, and return the SPA index.html for any other path.

spa_router.js

const ASSET_PATHS = ["/img/", "/css/", "/js/"];
const S3_BUCKET = "my-site-bucket";

// the SPA request router
async function handleRequest(request) {
	// lets parse the URL into a proper URL object
	const url = new URL(request.url);
	
	// if this is not an asset, return index.html
	const path = ASSET_PATH.some((path) => (url.pathname.startsWith(path))) ?
	 	url.pathname : 'index.html';
	
	// fetch the path from S3, include the original response 
	// so that headers, auth, etc aren't lost
	return fetch(
		`https://${S3_BUCKET}.s3.amazonaws.com/${path}`,
		response
	);
}

// add an event listener for fetch that calls the handler
self.addEventListener('fetch', event => {
  event.respondWith(handleRequest(event.request));
});

We now have an SPA router that will return our index.html for any request that is not in the predefined asset paths, and the appropriate asset for anything that is.

The API Gateway

Ok, on to the task at hand, the (very simple) API Gateway.

We are going to assume that front-end code has been udpated to make requests to https://api.bibs.codes/<service-name>/some/path and that those requests are intended for https://<service-name>.bibs.codes/some/path

The following code should intercept those requests and forward them to the correct service.

api_gateway.js

// The base url for the site
const baseURL = '.bibs.codes';

/**
The actual request handler
Remaps the URL from: api.bibs.codes/service_name to service_name.bibs.codes
**/
async function handleRequest(request) {
  const url = new URL(request.url);
  // skip the leading '/' and split the request
  const parts = url.pathname.substring(1).split('/');
  if (parts.length === 0 || parts[0] === '') {
    // if there is no service name, return a 404
    return new Response('Service Not Provided', { status: 404 });
  }
  const serviceURL = ''.concat(
    url.protocol, // use the same protocol
    '//',
    parts[0], // the service name
    '.bibs.codes/',
    parts.slice(1).join('/'), // the rest of the path after the service name
    url.search // the query string
  );
  return fetch(serviceURL, request);
}

/**
Register the request handler
**/
self.addEventListener('fetch', event => {
  event.respondWith(handleRequest(event.request));
});

Now can you register the worker above to match the path https://api.bibs.codes/* and start moving your front end code over to the new URL format.
